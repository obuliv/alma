⏺ The plan is written. Here's the shape of it:

  Foundation only — project structure, Dockerized docker compose deployment, the
  file-upload interface, and the DB layer. Extraction (2) and form-fill (3) are
  scaffolded as service interfaces + DB status fields so they slot in later
  without rework.

  Three containers, single origin (nginx proxies /api → api, so no CORS):
  - web — React/Vite build served by nginx
  - api — FastAPI/uvicorn, runs Alembic migrations on startup
  - db — Postgres 16, with files on a separate uploads volume (DB stores
  metadata + path, not blobs)

  DB schema anticipates that a passport + G-28 pair one form submission:
  applications groups documents, and each document gets one extraction_results
  row with a flexible JSONB data field (so step 2 can evolve without
  migrations). Status enums drive the upload → extracting → extracted lifecycle.

  Upload flow: POST /api/documents validates by magic bytes (not just
  client-sent content-type) + size limit, saves the file, records the row, and
  fires the extraction stub as a background task that manages status transitions
  — so step 2 only fills in real OCR/LLM logic.

  One thing I pushed on vs. the raw ask: I added an applications grouping table
  even though it's not strictly needed for upload. Reasoning — form population
  needs data from both documents together, so without a grouping concept step 3
  would force a schema migration later. It's cheap now and nullable, so it
  doesn't complicate the upload path.

  as several JP/PNGs, means one logical document can have many files. My current

  The change: split the logical document from its constituent files.

  one row.
  - document_files (pages/images) — id, document_id (fk), original_filename,
  content_type, file_path, file_size, page_order, created_at. Many rows per
  document.
  - extraction_results — stays one-per-document; extraction reads all files of
  that document and produces one merged record.

  Upload flow becomes: POST /api/documents accepts multiple files in one
  multipart request (files[] + doc_type) → creates one documents row + N
  document_files rows (ordered), then fires the extraction stub once over the
  whole set. Plus POST /api/documents/{id}/files to append more pages to an
  existing document. Each file is still validated individually (magic bytes +
  size). PDFs stay single-file-but-multi-page internally; images are the
  multi-file case.

     Context

     This is a greenfield project (empty folder). The end goal is a three-part
     system:
     1. File upload interface for passport + G-28 documents (PDF/JPEG/PNG)
     2. Data extraction into structured fields (name, DOB, country, passport #,
     address, attorney, firm, etc.)
     3. Form population via browser automation against a target form URL

     This plan scopes only the foundation: project structure, Dockerized
     deployment with docker compose, the File Upload Interface, and the database
     layer — designed so that extraction (2) and form-fill (3) drop in cleanly
     later. Those two are scaffolded as service interfaces + DB status fields,
     not implemented.

     Stack (confirmed with user): FastAPI backend · React (Vite) SPA frontend ·
     Postgres (SQLAlchemy + Alembic) · uploaded files on a local mounted volume
     · extraction & form-fill left as stubbed interfaces.

     /api → api:8000, so no CORS setup needed):

     Browser ──▶ web (nginx: serves React build + proxies /api) ──▶ api
     (FastAPI/uvicorn) ──▶ db (Postgres)

     uploads volume (files on disk)

     - api runs alembic upgrade head on startup, then uvicorn.
     - Files stored on disk under a named volume; DB stores metadata + file path

     Database Schema (initial migration)

     Anticipates that a passport + a G-28 together feed one form submission, so
     documents can group under an application.

     applications — groups documents for one form-fill run (nullable at first; a
     doc can exist unassigned)
     - id (UUID, pk), status (enum: new | ready | submitting | submitted | 
     failed), form_url (text, nullable), created_at, updated_at

     documents — a logical document (one passport, one G-28), which may span
     many files/pages
     - id (UUID, pk)
     - application_id (UUID, fk → applications, nullable)
     - doc_type (enum: passport | g28)
     - status (enum: uploaded | extracting | extracted | failed)
     - created_at, updated_at

     document_files — the actual uploaded files/pages belonging to a document
     (many per document)
     - id (UUID, pk), document_id (fk → documents)
     - original_filename, content_type, file_path, file_size
     - page_order (int) — order the files were uploaded / should be read
     - created_at

     ▎ A passport shot as separate JPGs (bio page, address page), or a 
     ▎ multi-page G-28 saved as several PNGs, becomes one documents row + N 
     ▎ document_files rows. A single multi-page PDF is one document_files row 
     ▎ (pages handled inside the PDF). Extraction reads all of a document's 
     ▎ files and produces one merged result.

     extraction_results — one per document, aggregating across all its files
     (filled in step 2)
     - id (UUID, pk), document_id (fk → documents, unique)
     - data (JSONB) — flexible structured fields so step 2 can evolve without
     migrations
     - raw_text (text, nullable), error (text, nullable), created_at

     Enums as Postgres enum types or string columns with app-level validation
     (simpler for migrations — plan uses string + Python Enum).

     File Upload Interface — Endpoints & Flow

     Backend (api/routes/documents.py):
     - POST /api/documents — multipart: files (one or many) + doc_type.
     Validates each file's type/size, saves each via storage.py, inserts one
     documents row (status=uploaded) + one document_files row per file (with
     page_order), then kicks off extraction once as a FastAPI BackgroundTask
     calling the stub ExtractionService over the whole document (sets extracting
     → placeholder → extracted/failed). Returns the document record with its
     files.
     - POST /api/documents/{id}/files — append more files/pages to an existing
     document (re-triggers extraction).
     - GET /api/documents — list with status + file counts.
     - GET /api/documents/{id} — detail incl. its files and extraction result.
     - GET /api/documents/{id}/files/{file_id} — stream a stored file back.
     - DELETE /api/documents/{id}/files/{file_id} — remove a mistakenly-added
     page.
     - GET /api/health — liveness/readiness.

     Validation (core/validation.py): allow only application/pdf, image/jpeg,
     image/png; verify via magic bytes (not just the header the client sends);
     enforce MAX_UPLOAD_MB (env, default 10). Reject with 400/413 + clear
     message.

     Frontend: single page — UploadForm (choose passport/G-28, select one or 
     multiple files via <input multiple>, preview the chosen page list, show
     upload progress + per-file validation errors) and DocumentList (poll GET 
     /api/documents, show status badge, file/page count, and — once extraction
     exists — the extracted fields). Uses same-origin /api calls.

     Stubs (so steps 2 & 3 slot in)

     - services/extraction.py: class ExtractionService with extract(document) ->
     ExtractionResult. Initial body returns an empty/placeholder data and marks
     status extracted, or is feature-flagged off. The upload flow already calls

     - services/form_fill.py: class FormFillService with fill(application, 
     form_url). Not wired to an endpoint yet; documented as the entry point for
     step 3 (Playwright/browser automation), which the user opted to add later.
