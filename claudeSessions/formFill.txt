❯ Wont this open a new tab/window in the browser and fill the values there?     

⏺ Good question — and no, not in the way you're picturing. Let me clear up the
  mental model, because it changes what the UI can show.

  Playwright drives its own browser, server-side — not your browser. When you
  click "Run" in the UI:

  - Your browser just sends an API request and then polls for status (like the
  document list does today).
  - The actual form-filling happens in a separate Chromium instance that 
  Playwright launches inside the backend container (the automation container).
  That browser lives on the server, not on your machine. In Docker it also runs
  headless (no visible window at all — BROWSER_HEADLESS=true).

  So there's no tab that pops open in your Chrome and fills itself in front of
  you. That's why I proposed taking a screenshot of the filled form and showing
  it back in the UI — that screenshot is your visual proof that it worked, since
  you can't watch the server's headless browser directly.

  If you genuinely want to watch it fill live, there are a couple of options,
  but each has a real cost:

  - Screenshot after fill (what I planned) — simplest, works in Docker, gives
  you an image of the completed form. No live viewing.
  - Headed browser you can watch — only works if the automation runs on your Mac
  directly (not in the container — a headless Docker container has no display).
  Means running the worker outside Docker for demos.
  - Live streaming (VNC / Playwright trace viewer) — you'd see the browser in
  real time, but it's meaningfully more infrastructure to wire up.

  Given all that, a few things worth deciding:

  1. Is a screenshot of the filled form enough proof for you, or do you
  specifically want to watch it fill live?
  2. Do you care whether it runs headless-in-Docker vs. a visible browser on
  your Mac?

  Which of those matches what you had in mind? Once I know, I'll fold it into
  the execution-model question and finalize the plan.

❯ I want to actually see and correct the form if needed. If playwright is not

⏺ Playwright is still the right tool — the issue isn't Playwright, it's where 
  the browser runs and whether it's headless. Let me lay out the real
  constraints and options, because "see it and correct it" pushes us in a
  specific direction.

  Why the container approach can't show you a window

  A browser inside the Docker automation container has no display — there's no
  screen for a window to appear on your Mac. That's why headless + screenshot
  was the default. To actually watch and interact, we need one of these:

  Option A — Headed browser on your Mac (run the worker locally).
  The api still runs in Docker and enqueues the run, but the Playwright worker
  runs as a plain Python process on your host. A real Chromium window opens on 
  your screen, you watch it fill each field, and you can grab the mouse/keyboard
  to correct anything and submit it yourself. Simplest path to true "watch +
  correct." Cost: for the demo the worker runs outside Docker (playwright 
  install chromium on the host, and we expose Postgres on 5432). Playwright
  leaves the browser open for you instead of closing it.

  Option B — Live browser streamed into the web UI (stays in Docker).
  Run headed Chromium in the container behind a virtual display (Xvfb) + VNC +
  noVNC, and embed that live view in a new tab of your web app via an iframe.
  You watch and click inside the web page. Architecturally clean (everything
  stays containerized, viewable from any machine), but it's meaningfully more
  infrastructure to build and debug.

  Option C — Correct in the UI first, then headless fill + screenshot.
  No live browser. The backend scrapes the fields and the LLM proposes {field: 
  value}; the UI shows that as an editable table where you fix any wrong values
  before filling; it then fills headless and returns a screenshot. You correct
  the data, but you don't watch or touch the live form.

  Alternatives to Playwright (for completeness)

  - Selenium — same story as Playwright (headed vs headless, host vs container);
  no advantage here.
  - Browser extension / userscript — could fill the form in your own browser
  tab, but your web app legally can't script another website's page
  (cross-origin), so this needs a real extension — large scope creep.
  - Prefilled URL (query-param links) — only works for forms that support it
  (e.g. Google Forms), breaks the form-agnostic requirement.
  - Hosted "cloud browser" (Browserbase/Steel/browserless) — gives you an
  embeddable live session like Option B without building VNC, but adds an
  external paid dependency + API key.

  My recommendation: Option A + the editable review table from C. You correct
  the proposed values in your own UI (reliable, easy), then a real Chromium
  window opens on your Mac so you watch it fill and take over to fix/submit
  anything the automation got wrong. Best of both, least new infrastructure.
  Playwright stays the engine.

⏺ Fair question, and my honest answer: you don't need to get rid of Docker, and 
  SQLite isn't worth the blast radius here.

  A few things worth separating:

  - You're not "keeping Docker for the whole app" — just the DB. docker compose 
  up -d db is one command, zero code changes, and it's already wired up. The
  API-on-host + DB-in-Docker split isn't extra complexity from this feature;
  it's the standard dev loop the repo already documents. The split exists only
  because the headed browser needs a display — that's unavoidable regardless of
  which DB you pick.
  - What SQLite actually buys you: it removes that one docker compose up -d db
  command, so you could run the demo with no Docker at all (just uvicorn + npm 
  run dev + a local .db file).
  - What it costs: it's a repo-wide persistence change, not a form-fill change.
  The existing models use Postgres JSONB (extraction_results.data, and my new
  fields/mapping columns), and 0001_initial.py is a hand-written Postgres
  migration. To run on SQLite you'd swap every JSONB to a portable JSON type and
  rewrite/guard the migration — touching the already-working upload +
  extraction flow that this take-home deliberately built on Postgres. That's
  real risk for the reward of avoiding one command.

  Functionally SQLite would work (we only store/read JSON dicts, no JSON
  querying), so it's not impossible — I just don't think trading a one-line
  docker compose up -d db for a foundation rewrite is a good deal.

  Which way do you want to go?
